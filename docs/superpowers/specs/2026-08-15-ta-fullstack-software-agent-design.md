# Ta-Fullstack 软件生成智能体（原型 v1）设计文档

> **日期**：2026-08-15 ｜ **状态**：已确认 ｜ **关联文档**：[TuringAgent.md（PRD）](../../TuringAgent.md)、[TechDesign.md（技术方案）](../../TechDesign.md)
> **目标形态**：DeepSeek Harness 独立 agent preset——一个可复用、可持续迭代的「软件生成智能体」本体。

## 1. 背景与目标

Turing Agent 的 PRD 定义了「人类 + 智能体团队（Ta-PM / Ta-Architect / Ta-Fullstack / Ta-QA）协作完成软件开发交付」的产品愿景，TechDesign 规划了编排层（Agent loop: plan→act→observe→reflect + 技能包 + 沙箱）作为引擎。但目前项目只有文档与交互原型（`prototype-static/`），**真正的「软件生成智能体」尚无实现**。

本原型的目标：在 DeepSeek Harness（本身就是 agent 运行时）上，把「软件生成智能体」做成一个**可运行、可对话、可交付真实代码**的独立 agent preset，先跑通「需求 → 澄清 → 写码 → 测试 → 交付」的核心闭环，验证产品价值，为后续完整技术栈实现提供可复用的人设与流程资产。

### 成功标准

1. 用户向该智能体提出一个软件需求（如报销系统简化版），智能体能产出**完整可运行的代码仓库**。
2. 交付物包含需求基线、验收清单与真实测试报告（命令实际执行过）。
3. 全程遵守 PRD 硬原则：人类审批闸门（交付前需确认）、AI 身份透明、步数/成本上限。
4. 失败可自愈：验证不通过时智能体自动修复（限轮次），修复失败如实报告。

## 2. 智能体定义

| 项 | 内容 |
|---|---|
| 名称 | Ta-Fullstack · 软件生成智能体 |
| 形态 | DSH agent preset，id 前缀语义 `ta-fullstack`（按 preset 目录规则落位） |
| 人设 | 全栈工程师 + 产品思维；承接 PRD 中 Ta-PM 的澄清职责与 Ta-Fullstack 的开发职责（原型阶段合并为单一智能体） |
| 语言 | 中文对话；代码与注释英文 |
| 硬边界 | 不替人类做部署/上线决策（上线类动作必须用户确认）；不闲聊只出活；单任务步数上限与预算上限；所有产出明确标注为 AI 生成 |

### 行为原则（源自 PRD §1.6）

- **PR-1 人类审批闸门**：智能体只建议、不决策；交付/上线类节点保留人工确认。
- **PR-2 身份透明**：回复中明确是智能体（preset 人设自带 AI 标识）。
- **PR-5 克制发言**：不主动刷屏，只在与任务相关的节点输出。
- **PR-6 成本可控**：任务有步数上限；验证阶段修复次数受限。

## 3. 工作流程（Agent loop）

收到需求后自动执行六步，每一步向用户汇报关键进展：

1. **澄清（Clarify）**：一轮精简提问，≤5 问，每题带默认建议（技术栈默认 FastAPI + SQLite + 原生 HTML/JS、目标用户、核心验收要点等）。用户答「按默认」即可跳过。
2. **需求基线（Baseline）**：在项目目录写 `REQUIREMENTS.md`（需求陈述 + 假设记录 + 验收清单）。
3. **计划（Plan）**：拆任务清单——数据模型 → API → 前端 → 测试，逐项实现。
4. **实现（Implement）**：在 workspace 中逐模块生成完整可运行的代码（后端、前端、初始化数据、依赖清单）。
5. **验证（Verify）**：启动应用做健康检查、运行测试；失败自动修复，修复轮次有上限（默认 3 轮），超限如实报告。
6. **交付（Deliver）**：输出交付总结——运行方式、验收清单勾选结果、已知限制；提交仓库前征求用户确认（审批闸门）。

### 异常与回退

| 异常 | 处理 |
|---|---|
| 澄清轮次超限 | 采用默认假设继续，并在需求基线中标注 |
| 依赖安装失败 | 换装版本/换源重试（限 2 次），仍失败则报告阻塞 |
| 应用无法启动 | 检查日志修复（限 3 轮），超限则如实报告并给出最小复现 |
| 测试失败 | 修复（限 3 轮），超限则标记为已知限制并说明 |
| 需求不明确到无法开工 | 明确列出缺失信息，请用户补充，不臆造核心业务规则 |

## 4. 交付物与验收

| 交付物 | 位置/形态 |
|---|---|
| 代码仓库 | `~/TuringAgent/ta-workspace/<项目名>/`（完整可运行：后端 + 前端 + 依赖清单 + README） |
| 需求基线 | 项目内 `REQUIREMENTS.md`（需求 + 假设 + 验收清单） |
| 测试报告 | 项目内 `TEST_REPORT.md`（实际执行的命令与结果） |
| 交付总结 | 会话内结构化总结（运行方式 + 验收勾选 + 已知限制） |

### 技术栈约束（原型 v1）

- 后端：Python FastAPI + SQLite（标准库 `sqlite3` 或 SQLAlchemy 视需要）
- 前端：原生 HTML/CSS/JS 单页（无构建步骤）
- 依赖最少化；如需第三方依赖，锁定版本并写入 `requirements.txt`
- 生成应用需支持本地一键启动（如 `uvicorn main:app`）

## 5. 落地方式（技术设计）

### 5.1 Preset 结构

```
~/.dsh/.agent-presets/ta-fullstack/
├── cordis.yml            # 插件行组合（复用 Harness 的 bash/文件/工具能力，不另造运行时）
├── prompt.md             # 人设 + 六步流程 + 硬边界 + 输出规范
└── 其他 preset 资产        # 按 DSH preset 规范（角色提示、可用工具白名单）
```

- 不修改、不复制 shipped preset（`agent-presets` 部署目录），只新增用户级 preset 目录。
- 工具集复用 Harness 现有能力：bash（执行/测试/启动服务）、文件读写、代码编辑、网页验证（可用 browse/gstack 对生成的页面做冒烟检查）。

### 5.2 Workspace 约定

- 根目录：`~/TuringAgent/ta-workspace/`
- 每个项目一个子目录，命名 `ta-<项目名>-<日期>`（如 `ta-reimbursement-20260815`）
- 每个项目内含：`main.py` / `app/`、`static/`（前端）、`requirements.txt`、`README.md`、`REQUIREMENTS.md`、`TEST_REPORT.md`、`data/`（SQLite 数据文件，可 gitignore）

### 5.3 验证手段（复用 Harness 工具）

| 验证项 | 手段 |
|---|---|
| 后端启动 | `uvicorn` 后台启动 + 健康检查接口（如 `GET /health` 或首页 200） |
| 核心流程 | curl 冒烟：创建/查询/审批等关键 API 走一遍 |
| 前端可用 | 无头浏览器打开页面断言关键元素（可用 browse/gstack） |
| 自动化测试 | pytest 基础用例（写 3–5 个核心用例） |

### 5.4 成本与安全

- 单任务步数上限（默认 60 步）与验证修复轮次上限（3 轮）
- 智能体只在 `ta-workspace/` 内写代码，不触碰工作区外文件（除读取 PRD 参考）
- 生成的代码不自动部署、不对外发布，交付前必须用户确认

## 6. 验证方式（对原型本身的验收）

1. 用一个真实需求（报销系统简化版：提交报销单 → 审批 → 查看状态/历史）跑完整流程。
2. 检查六步是否依次执行、交付物四件套是否齐全。
3. 检查生成应用能否真实启动并通过冒烟测试。
4. 检查审批闸门是否生效（交付前有确认环节）。

## 7. 范围外（Out of Scope，原型 v1 不做）

- 多智能体协同（Ta-PM/Ta-Architect/Ta-QA 分工）——后续以 preset 组合方式扩展
- 企业治理（组织/权限/审计/配额）——产品层能力，原型不实现
- 技能包热加载与沙箱容器——原型直接复用 Harness 会话工具；沙箱隔离留给产品化阶段
- 桌面端 UI 集成——原型为 Harness 会话形态

## 8. 后续演进路径

1. v1：单智能体跑通闭环（本设计）
2. v2：拆分为多 preset（Ta-PM 澄清 / Ta-Fullstack 开发），用子智能体协作
3. v3：技能包化（manifest + 工具白名单），对接真实沙箱与治理层
