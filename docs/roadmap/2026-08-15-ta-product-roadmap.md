# Turing Agent（Ta）产品开发路线图

> **日期**：2026-08-15 ｜ **状态**：评审中 ｜ **关联**：[PRD v2.0](../TuringAgent.md)、[TechDesign v1.0](../TechDesign.md)、[原型 prototype-static](../prototype-static/)、[智能体 preset 原型](../docs/superpowers/specs/2026-08-15-ta-fullstack-software-agent-design.md)
> **一句话**：IM 聊天软件是壳，智能体团队是引擎，企业治理是信任底座——本路线图把 PRD 的里程碑落成可执行、有依赖顺序、可验收的开发计划。

---

## 1. 项目本质与核心原则

**产品形态**：企业 IM 聊天软件，人类成员与智能体团队（Ta-PM / Ta-Architect / Ta-Fullstack / Ta-QA）在同一会话中协作，完成「需求 → 澄清 → 评审 → 交付 → 验收」的软件开发闭环。

**开发排序必须服从的三条产品原则（PRD §1.6）：**
1. **PR-1 人类审批闸门**：审批/上线类能力必须从第一天存在（不是后补），否则智能体不可信、不敢放权。
2. **PR-6 成本可控**：模型配额/熔断必须从第一天内置，否则商业模型不成立。
3. **PR-5 克制发言**：静默策略与评测集是发布门禁，不是优化项。

## 2. 资产盘点与复用策略

| 已有资产 | 形态 | 在路线图中的转化方式 |
|---|---|---|
| `TuringAgent.md`（PRD v2.0） | 需求文档 | 需求基线：功能优先级（P0/P1/P2）即排期依据 |
| `TechDesign.md` | 技术方案 | 架构约束：Go 模块化单体 + TS 编排层 + Model Gateway |
| `prototype-static/` | 零依赖静态原型 | **交互规格的可执行样本**：每个页面/组件是前端实现的任务书与验收基准 |
| `~/.dsh/.agent-presets/ta-fullstack/` | 可运行的智能体 preset | **智能体运行时 v0**：六步闭环已跑通，直接作为编排层种子 |
| DeepSeek Harness | agent 运行时框架 | 复用其 preset/工具/子代理机制，作为智能体引擎底座（见 D1） |

**核心复用洞察**：智能体引擎（最难、最不确定的部分）已有一个真实可运行的原型；IM 交互（最考验细节的部分）已有全交互原型。缺口集中在**后端服务**与**产品化封装**——路线图应把火力集中在这里。

## 3. 子系统依赖图

```
组织/权限/审计（BL-9 基础） ──► 审批流引擎（BL-4）──► 需求/变更/上线闭环（BL-1/5/6）
        │                            │
        ▼                            ▼
IM 消息引擎（BL-7 核心）◄── 确认卡片 / 任务卡（所有闭环的 UI 载体）
        │
        ▼
智能体运行时（preset + 编排 + 静默策略）──► 需求澄清 / 代码生成 / QA 交付
        │
        ▼
模型网关（多模型路由 / 配额 / 熔断 / 计量）──► 成本控制（PR-6）
        │
        ▼
沙箱执行（代码生成安全门禁，Phase 1 简化 / Phase 2 完整）
```

**排序铁律**：
1. IM 消息引擎是**一切 UI 的脊柱**——先于所有业务闭环。
2. 组织/权限是**审批的前提**——先于审批流。
3. 模型网关是**智能体成本的前提**——与智能体接入同步做，不后置。
4. 审批（哪怕单级）先于**上线/变更**——PR-1 闸门不后补。

## 4. 战略决策点（需产品负责人拍板）

| # | 决策 | 选项 | 建议 |
|---|---|---|---|
| **D1** | 智能体运行时底座 | A. 复用 DeepSeek Harness（preset 即智能体，服务端跑会话）<br>B. 自建 TS 编排层（TechDesign 原案） | **A（MVP）→ B（Phase 2 平滑替换）**：A 已跑通、成本最低；把「技能包/Agent loop」抽象成内部接口，B 落地时按接口替换，业务无感 |
| **D2** | 客户端形态 | A. Web 优先（原型直接演进为 React 组件）<br>B. Tauri 桌面优先（PRD 原案） | **A（MVP）**：浏览器即开即用、迭代最快；Phase 2 用 Tauri 包同一套 Web 资产（冷启动/通知/拖拽 NFR 在壳层补齐） |
| **D3** | MVP 后端规模 | A. Go 模块化单体全量（TechDesign）<br>B. 精简到必需模块 | **B（MVP 只做：认证+组织基础+聊天+审批单级+审计+网关）**，其余模块 Phase 2 加；单体结构不变，避免返工 |
| **D4** | 数据库/部署 | PG（RLS 预留）+ Redis + 单机 Docker Compose 起步 | **维持 TechDesign**；私有化安装器 Phase 2 再做 |

> 这四项一旦拍板，Phase 0 即可开工。建议：D1=A、D2=A、D3=B、D4=TechDesign 原案（本路线图后续按此假设展开；若改判，仅影响对应阶段的构建内容，依赖顺序不变）。

### 4.1 决策记录（2026-08-15 已拍板）

| # | 决策 | 结论 |
|---|---|---|

## 5. 阶段路线图

### Phase 0：地基（第 1–4 周）——把「文档+原型」变成「可运行的骨架」

**目标**：一个能打开、能登录、能发消息、能 @智能体得到回复的最小竖切（thin vertical slice）。

| 里程碑 | 内容 | 复用 |
|---|---|---|
| M0.1 仓库与契约 | monorepo 初始化（apps / services / packages）；`packages/contracts` 类型定义（消息/会话/审批/任务） | TechDesign §3 |
| M0.2 后端骨架 | Go 单体 + PG schema 迁移 + 认证（演示登录 + OIDC 预留）；WS 消息推送（先推后持久） | TechDesign §2/§9 |
| M0.3 IM 消息引擎核心 | 会话/群/消息 CRUD、已读、seq 顺序、文件上传（MinIO） | 原型 scripts/storage.js 的语义搬进后端 |
| M0.4 模型网关最小版 | 1 个模型供应商适配 + token 计量 + 配额熔断接口 | TechDesign §2 网关层 |
| M0.5 智能体接入 | 消息路由（@触发/静默策略）→ 编排层 → 现有 ta-fullstack preset 会话 → 回复入群 | ✅ 已有 preset 直接接 |
| M0.6 前端竖切 | 登录页 + 单会话聊天窗（React，参照原型 index.html 组件化） | 原型 1:1 组件化 |

**验收门槛（工程级）**：浏览器打开 → 演示登录 → 与 Ta-Fullstack 对话收到回复（回复走真实 LLM）；消息落库、刷新不丢；WS 推送延迟 P95 < 500ms。

### Phase 1：MVP（第 5 周 – 第 3 月）——PRD Phase 1 的工程化版本

**目标**：5 家种子客户真实跑通「需求 → 澄清 → 评审 → 交付 → 验收」闭环。

| 里程碑 | 内容 | 对应 PRD |
|---|---|---|
| M1.1 三栏工作台 | 会话列表 / 消息流 / 右侧上下文面板（进度/看板/记忆/交付物）组件化落地 | FR-CHAT 全组 |
| M1.2 组织与权限 | 租户/部门/成员/角色 + RBAC 基础 + 操作审计（append-only） | FR-ORG-01/02/03/06、FR-PERM-01/03 |
| M1.3 群聊完整化 | @提及、AI 身份标识、确认卡片、静默策略（评测集 ≥ 95% 门禁）、文件、语音转文字 | FR-CHAT-03/04/05/07/12、FR-TASK 轻量 |
| M1.4 智能体四角色 | Ta-PM（澄清）/ Ta-Architect（评审意见）/ Ta-Fullstack（写码交付）/ Ta-QA（测试）——从单一 preset 扩展为多 preset + 子代理调度 | TechDesign §7.1 |
| M1.5 单人审批 + 记忆文档 | 确认卡 → 审批状态机（单级）；记忆自动沉淀 + 版本留痕 | FR-APP-01、FR-MEM |
| M1.6 桌面壳（可选提前） | 若 D2 改判桌面优先，此处用 Tauri 包壳；否则 Phase 2 | FR-DESK |

**验收门槛**：PRD §13 Phase 1 门槛（5 家种子客户跑通 BL-1/2/3/4/5/7/8 基础版 + BL-9；NFR 达标；静默准确率 ≥ 95%）；北极星指标 WCD 开始采集。

### Phase 2：多用户协作增强（第 3 – 6 月）

**目标**：≥ 50 家付费企业；需求交付周期缩短 ≥ 40%；企业 8 周留存 ≥ 60%。

| 里程碑 | 内容 |
|---|---|
| M2.1 多级审批引擎 | 会签/或签/条件/转办/超时升级（状态机 + 配置界面） |
| M2.2 统一任务看板 | 人类+智能体混合看板、拖拽、统计瓦片、日报周报（原型 board.html 落地） |
| M2.3 CI/CD 集成 | 代码评审、安全扫描门禁、部署联动（两级上线审批） |
| M2.4 技能包管理 | manifest + 工具白名单热加载；企业知识库；智能体配额熔断全量 |

| M2.6 运行时替换 | 若 D1 改判，此处把 Harness 底座替换为自建编排层（按 Phase 0 抽象接口） |

**验收门槛**：PRD §13 Phase 2 门槛 + 等保三级评测启动。

## 6. 关键路径与周数估算（单人/小团队）

```
Phase 0（4 周）→ Phase 1（8 周核心闭环）→ 种子客户试用（2 周）→ Phase 1 收尾（2 周）
            ↘ Phase 2（12 周）→ Phase 3（持续）
```

**最长的关键路径**：IM 消息引擎 → 智能体接入 → 澄清/交付闭环 → 种子客户验收。**智能体引擎不在关键路径上**（v0 已跑通），这是当前最大的时间优势。

## 7. 风险与红线

| 风险 | 缓解 | 红线（触发即重估） |
|---|---|---|
| 智能体回复质量不稳（静默准确率 < 95%） | 评测集从 Phase 0 开始建；发布门禁前置 | 连续 3 周门禁不过 → 砍功能范围而非放宽门禁 |
| 后端工作量吞噬进度（Go 全栈） | D3 精简模块；消息引擎用成熟模式；先竖切后横切 | Phase 1 中期未达 M1.3 → 重估 D3 或引入现成 IM 底座 |
| 审批/治理复杂度拖慢闭环 | MVP 单级审批先行，多级后置 | — |
| 模型成本失控 | 网关配额/熔断第一天内置（PR-6） | 单任务成本超预算 2 倍持续 2 周 → 强制分层路由 |
| 产品定位漂移（做回通用 IM） | 每周用「软件交付闭环」自检所有功能 | 新功能不服务 BL-1…9 任一闭环 → 不做 |
